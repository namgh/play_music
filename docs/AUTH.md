# 로그인 설계

**결정 (2026-11-24): 로그인은 구글 하나만 쓴다.** 가입 화면·비밀번호·확인 메일·재설정이 전부 없어지고, 화면에는 "구글로 계속하기" 단추 하나만 있다. 처음 누르면 계정이 바로 만들어진다.

이메일·비밀번호 가입 코드는 서버에 남아 있지만 **꺼져 있다**(`PASSWORD_AUTH_ENABLED=false`, 꺼져 있으면 `/v1/auth/signup`·`/login` 은 404). 다시 열 일이 생기면 그 값만 켠다 — 아래 "두 수단이 만날 때" 규칙은 그때를 위해 남겨 둔다.

## 구글만 쓰는 것의 값

| 얻는 것 | 치르는 것 |
|---|---|
| 가입이 단추 하나 — 비밀번호·확인 메일이 없다 | 구글 계정이 없거나 회사·학교에서 막힌 사람은 로그인하지 못한다 |
| 우리가 비밀번호를 보관하지 않는다 (유출될 것이 없다) | 구글 쪽 장애나 계정 정지 때 그 사람은 들어올 길이 없다 |
| 메일 발송(SMTP)에 가입이 묶이지 않는다 | |

두 번째 줄을 견디게 하는 것은 **로그인 없이도 곡을 만들고 파일로 저장할 수 있다**는 점이다. 로그인이 막혀도 작업물은 내 컴퓨터에 있다. 이 성질은 계속 지켜야 한다.

## 설치형 앱에서의 구글 로그인

설치형이 주 제품이므로 이 경로가 중심이다. 앱 안의 창이 아니라 **시스템 브라우저**에서 로그인한다 — 구글이 앱에 든 창에서의 로그인을 막고, 사용자도 주소창이 보여야 진짜 구글인지 안다.

```
앱        127.0.0.1 의 빈 포트를 열고, 검증값(verifier)을 만들어 그 해시(challenge)만 서버에 준다
          GET /v1/auth/google/start?desktop_port=…&desktop_challenge=…
브라우저   구글 로그인 → 서버 콜백 → http://127.0.0.1:포트/callback?code=한번짜리코드
앱        POST /v1/auth/desktop/exchange { code, verifier } → 세션(리프레시 쿠키는 앱의 쿠키 저장소에)
```

- 브라우저 쪽에는 세션 쿠키를 심지 않는다. 브라우저가 받는 것은 한 번짜리 코드뿐이다.
- 코드는 **한 번, 2분 안에만** 쓰이고, 로그인을 시작한 앱만 아는 검증값이 맞아야 한다. 같은 컴퓨터의 다른 프로그램이 127.0.0.1 로 온 코드를 엿봐도 쓸 수 없고, 한 번 틀리면 코드가 사라진다.
- 돌아갈 주소는 `127.0.0.1` 고정이고 포트 숫자만 받는다 — 다른 곳으로 보낼 수 없다.
- 구현: `desktop/main.cjs`(`resona:google-login`), `src/api/auth.ts`(`loginWithGoogle`), 서버 `accounts/router.py`.

웹은 같은 `/google/start` 로 주소를 받아 구글로 가고, 돌아오면 서버가 심어 둔 리프레시 쿠키로 세션을 받는다.

## 참고 — 이메일 가입을 다시 열 때의 규칙

아래는 `PASSWORD_AUTH_ENABLED=true` 일 때의 동작이다. 지금은 쓰지 않는다.

### 계정은 하나, 로그인 수단은 여러 개

```
users                     사람 한 명 (곡·워크스페이스·결제가 여기에 달린다)
 └─ auth_identities       로그인 수단 — (provider, subject)
      ├─ password / 이메일          비밀번호 해시(Argon2id)
      └─ google   / 구글 sub        구글이 주는 바뀌지 않는 사용자 번호
```

두 수단 모두 로그인에 성공하면 **같은 세션**을 받는다 — 10분짜리 액세스 토큰(JWT)과 30일짜리 리프레시 쿠키(HttpOnly, 쓸 때마다 교체, 재사용이 보이면 전 세션 끊기).

### 흐름

**이메일 가입**

1. 이메일 + 비밀번호(10자 이상) → 계정이 `pending_verification` 으로 생기고 확인 메일이 간다.
2. 확인 전에도 **편집·저장은 된다** (확인 메일 때문에 첫 경험이 끊기면 안 된다). 새 결제만 확인 뒤에.
3. 메일의 링크를 누르면 `active`.

**구글 로그인** (Authorization Code + PKCE)

1. `GET /v1/auth/google/start` → 구글 화면 → `GET /v1/auth/google/callback`.
2. 넷을 전부 검증한다 — `state`(한 번 쓰고 버림) · PKCE · `nonce` · **`aud`**(우리 앱에 발급된 토큰인가).
3. 아래 순서로 사용자를 찾는다.

### 두 수단이 만날 때 (가장 틀리기 쉬운 곳)

구글로 들어온 사람을 우리 계정에 맞추는 순서:

| 순서 | 경우 | 처리 |
|---|---|---|
| 1 | 그 구글 `sub` 가 이미 연결돼 있다 | 그 계정으로 로그인. 구글에서 이메일을 바꿨어도 같은 계정이다 |
| 2 | 같은 이메일의 계정이 있고, 구글이 그 이메일을 **확인해 줬다** | 그 계정에 구글을 **연결**한다 (곡이 두 계정으로 갈리지 않게) |
| 2-a | …그런데 그 계정이 **이메일 확인을 한 적이 없다** | 연결하되 **기존 비밀번호와 세션을 전부 끊는다** (아래) |
| 2-b | 구글이 그 이메일을 확인해 주지 않았다 | **거절** — 남의 주소로 구글 계정을 만들어 계정을 가져갈 수 있다 |
| 3 | 아무것도 없다 | 새 계정 + 개인 워크스페이스. 비밀번호 없이 만든다 |

**2-a 가 왜 필요한가 — 미리 만들어 둔 계정 탈취.** 공격자가 피해자의 이메일로 먼저 가입해 둔다(확인 메일은 못 누른다). 나중에 피해자가 구글로 들어오면 같은 이메일이라 계정이 합쳐지는데, 이때 공격자가 걸어 둔 비밀번호가 살아 있으면 공격자도 그 계정에 들어온다. 그래서 **확인된 적 없는 계정에 붙을 때는 기존 비밀번호와 세션을 버린다.** 진짜 주인이 가입만 하고 확인을 안 했던 경우라면 구글로는 그대로 들어오고, 비밀번호가 필요하면 재설정 메일로 다시 건다. (2026-11-24 추가, `test_linking_an_unverified_account_drops_its_password_and_sessions`)

반대 방향 — **구글로 가입한 사람이 비밀번호도 쓰고 싶을 때**는 "비밀번호 재설정" 메일을 받아 건다. 이메일의 주인임을 메일로 증명하므로 따로 연결 절차가 필요 없다.

### 그 밖에 지키는 것

- 로그인 실패는 **계정이 있는지 알려 주지 않는다** — 같은 문구, 같은 응답 시간.
- 비밀번호 복잡도 규칙(대문자·특수문자)은 걸지 않는다. 길이만 본다.
- 비밀번호를 바꾸거나 재설정하면 다른 기기의 세션을 끊는다.
- 탈퇴는 30일 유예 뒤 삭제, 그 안에는 복구할 수 있다.
- 로그인·연결·비밀번호 변경은 감사 로그에 남는다.

## 아직 할 것

1. **실제 구글 계정으로 돌려 보지 않았다.** 서버 쪽은 구글 응답을 흉내 낸 시험으로 확인했고, 설치형의 브라우저 왕복은 실제 OAuth 클라이언트가 있어야 눌러 볼 수 있다. Google Cloud Console에서 클라이언트를 만들어 `server/.env` 에 넣어야 한다(`README.md` 서버 절).
2. **계정 삭제 확인.** 비밀번호가 없으니 삭제할 때 본인 확인은 구글 재로그인으로 해야 한다 — 지금은 구글 계정이면 확인 없이 진행된다.
3. 2단계 인증은 구글 계정의 것을 따른다. 애플·카카오 로그인은 필요해지면 같은 구조(`auth_identities`)에 붙인다.
